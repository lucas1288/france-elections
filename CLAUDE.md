## Project summary

A React + MapLibre GL JS interactive choropleth map of French election results (currently: Présidentielles 2012, 2017 & 2022, Législatives 2012, 2017, 2022 and 2024, rounds 1 & 2 each). Users can view results at commune or circonscription granularity (per the election's manifest entry), click geographic units to see detailed results in a sidebar, zoom into overseas territories, and explore Français à l'étranger results on a small world map. Long-term goal: all presidential elections since 1965 and all legislatives since 1958 (see "Expansion roadmap" notes in conversation history / README).

**Owner**: lucas (lucas1288 on GitHub, lucas.riveill@gmail.com)
**Stack**: React 19, TypeScript, Vite 6, Tailwind CSS 3, MapLibre GL JS 5, PMTiles 4, Zustand 5, TanStack Query 5, D3-geo, topojson-client

## Key architectural decisions

### 0. Manifest-driven elections (`public/data/elections/index.json`)
Each election declares: `type`, `year`, `rounds`, `label`, `granularities` (which tabs exist), and `geometry` (version ids `{ admin, circo }` resolved to PMTiles URLs via `TILE_SOURCES` in `FranceMap.tsx`). Granularity availability comes from the manifest, NOT from 404 sniffing. When the selected election lacks the active granularity, an App effect switches to the first available one. A geometry-version change triggers `map.setStyle(makeStyle(geom))` + re-sync (path exists but is dormant while all elections share `admin-2022`/`circo-2010`).

### 0c. Color modes (`colorMode` in the store)
The choropleth can be colored three ways (Zustand `colorMode`): `leader` (winning candidate/nuance — default), `party` (single force, territories shaded by score-vs-national RATIO — `utils/gradient.ts` `partyRatioShade`), `abstention` (grey ramp). `utils/territoryColor.ts` is the shared per-territory color function used by FranceMap (dept + gradient layers) and the overseas orbit (both platforms) so every surface stays consistent. Leader rides the lightweight choropleth; abstention rides the choropleth's `abstention` field; the party gradient needs the full per-territory data (loaded per tab) + the national baseline from `utils/nationalResults.ts` `computeNationalTotals` (dept data sums to national exactly). Triggers: on desktop the sidebar `NationalSummary` rows (click a force → its party view via `togglePartyMode`, click again → leader; the participation block toggles the abstention ramp); on mobile the "Résultats nationaux" sheet rows (`AffichageSheet`) — same model on both. **The mobile bottom-left palette chip that used to open that sheet was REMOVED (July 20, 2026, lucas)** — the sheet now opens only from the national snippet card's "Détails" affordance. NOTE the consequence: the snippet renders only at the unzoomed overview (`!clickedCommune && !focusedTerritory && !zoomedAway`), so while zoomed in / with a territory selected there is no entry point to the national sheet — return to the overview (back button) to reach it.

**C1 — party mode has a SECOND reading: SEATS (`src/utils/partySeats.ts`, Aug 7 2026).** lucas: "when clicking on a party/alliance, show — with the colour of the Alliance, where their candidates have been elected; with dark grey, where their candidate has lost the 2nd tour" (reference: Le Monde's 2024 T2 map, legend counts included). This is a THIRD reading of the choropleth, not a tweak to `partyRatioShade`.
- **Where it applies (lucas's call): the circonscriptions tab of a LEGISLATIVE election, automatically — no new control.** The circo IS the seat-bearing unit, so the question genuinely changes with the tab; the communes tab and every presidential keep the score gradient, which is the only reading those units support. One gate, `seatContext()` in FranceMap, decides it; `territoryColor` takes an optional 7th `seats` arg and callers that shouldn't get it simply don't pass it. The overseas orbit's `circoColor` passes it too, so the rings agree with the map; the disc fills and the phone's aggregate button do NOT (they are département-level sums, which have no seat).
- **States: 3 at T2, 4 at T1** (lucas picked four). T2 = élu / éliminé au 2nd tour / pas de candidat. T1 adds **qualifié pour le 2nd tour**, because a circo that isn't decided outright sends candidates to a runoff and that is a real, different result — otherwise the map would silently change meaning when you switch round, which is exactly what the timeline strip encourages you to do. `elected` at T1 means won outright; the parsers already resolved that into the flag, so nothing re-derives it.
- **Qualification is the legal rule**, not a heuristic: ≥12,5 % of INSCRITS, with the fallback that the top two go through if fewer than two clear the bar. Validated against the official 2024 configuration — the rule yields **307 triangulaires + 5 quadrangulaires + 189 duels** against the reported 306/5; the single difference is Drôme 2, where the third candidate sits **0,019 points above the bar (~15 voters)**. CAVEAT to state when reading a T1 map: this is who qualified ON THE NIGHT. Whether they then stood is a T2 fact — 2024's ~200 désistements are the obvious case.
- **GOTCHA that produced wrong seat counts and would have shipped: `partyCodeSet` is the WRONG basis for seats.** It adds the alliance's member parties, which is right for the score gradient (a vote for a component is a vote for the alliance) but wrong for a counted, official quantity: it gave **NFP 192 seats against the official 178** (+DVG 12 +SOC 2) and Ensemble 156 against 150 — contradicting the Pourcentages/Sièges switch *on the same screen*. `seatCodeSet(party)` (the nuance alone) is what the seat path uses, including the `*-won` outline highlight, which in this view means "won the seat", not "came 1st".
- **`components/results/SeatLegend.tsx`** is the key, self-gating (it re-tests the same three conditions) and mounted by BOTH `NationalSummary` (compact) and `AffichageSheet` (touch). The counts are the point: the map shows a pattern the reader otherwise can't quantify. Verified live — 2024 T2 NFP 178/174/225, RN 125/332/120, both summing to 577 and matching the official composition; 2024 T1 RN 37/389/75/76.
- The two greys flip with the theme like `DEFAULT_COLOR` does (`ELIMINATED_LIGHT #64748b` / `ELIMINATED_DARK #94a3b8`): "éliminé" has to stay distinct from the no-data neutral AND the background in both themes, and one fixed grey disappears into a dark map.

### 0b. Palette-in-data (`palette.json` per election)
Each election ships a small `palette.json`: `byName` (candidate → hex, presidentials) and/or `parties` (party/nuance code → `{label, color, alliance?, members?, family?}`, legislatives).

**Political families (two-axis P3, July 2026)**: `public/data/elections/families.json` is the GLOBAL cross-election registry — `blocs` (gauche/centre/droite/extrême droite/autres) + `families` (14 lineages, each `{label, color, bloc, order}`, order = left→right spectrum). Every palette `parties` entry carries `family: <id>` (presidentials too — their `parties` map covers all candidates' party codes, so no byName annotation is needed). Decisions (lucas): Macronisme merged into `centre` (continuity of the independent centre — Bayrou 2007/2012, UDF); Reconquête its own family (far-right split: bloc `extreme-droite`, own color); PCF its own family — alliance years are absorbed by the `union-gauche` family (NUPES/NUP, NFP/UG) + the bloc level, whose series stay continuous. Family colors are canonical for CROSS-ELECTION surfaces only (future time-series/timeline, P4–P5) — per-election views keep their palettes. App side: `useFamilies()` hook + `src/utils/families.ts` (`familyOfParty`, `familiesInOrder`) — loaded but not yet consumed by any UI. **`node scripts/validate-families.mjs`** checks every party/nuance code in every manifest election resolves to a defined family+bloc — run it after adding an election or editing a palette (gates future ingestions). `getCandidateColor(name, index, party, palette)` resolves palette first, then the legacy built-in 2022 tables, then a categorical fallback. For legislatives, the "candidates" of dept-level AND commune-level data and all choropleth leaders are NUANCE labels (the ministry's 2022 nuance codes already encode pre-electoral alliances: NUP, ENS); per-circo full data keeps real candidate names with nuance as `party` (+ `elected: true` for seat winners — feeds a future hemicycle view). Commune-level legislative results come from the ministry's `subcom` file (one row per commune×circo); `scripts/parse-legislatives-2022.mjs` aggregates them to the commune by nuance (summing across the circos a commune spans — Paris/Lyon/Marseille), so a commune split across circonscriptions still has a well-defined leading nuance.

**Législatives 2024** (`scripts/parse-legislatives-2024.mjs`, sources in `data-sources/legislatives-2024/`) emits the identical file set but parses a *different* ministry format: the 2024 "résultats définitifs" CSVs are one file per level (circo / commune / bureau / dpt), labeled headers, UTF-8/CRLF, with candidate columns in repeating 9-wide blocks `[Panneau;Nuance;Nom;Prénom;Sexe;Voix;%Ins;%Exp;Elu]`. Two format gotchas: (1) **round-2 files quote text/code fields** (`"01";"0101"`) while round-1 files don't — `readRows` strips wrapping quotes per cell or round-2 codes come out garbage; (2) codes are normalised to match the existing `circo-2010`/`admin-2022` tiles exactly (`ZZ`→`99`, `ZX`→`977`, DOM `971`–`988` already dept-prefixed, métropole+Corse `dept.pad2 + circoNum`; commune codes pad 1-digit-dept rows to 5). Geometry is unchanged from 2022 (no new tiles). PLM arrondissements are aggregated from the 2024 bureau file inside the same script (arr = `floor(codeBV/100)`) and injected into the commune outputs. **Dept, commune AND arrondissement outputs are keyed by NUANCE** (`name` = nuance label, `party` = code), like 2022 — only the per-circo `-circ.json` keeps real candidate names. This matters for coloring: the whole choropleth/dot/dept color path resolves a nuance LABEL → code → palette, so a commune whose `leadingCandidate` is a person name (the bug we hit: `readCandidates` builds `"Prénom NOM"`) silently fails the palette lookup and renders a fallback colour. Keep `parseCommunes` grouping by nuance. 2024 nuances differ: `UG` = Nouveau Front populaire (alliance), `UXD` = Union de l'extrême droite, `ENS`/`RN`/`LR` as before. Validated: 577 circo codes == 2022 set; R2 seat composition (UG 178, ENS 150, RN 125, …, total 577) and R1 national shares (RN 29.3 / NFP 28.0 / ENS 20.0) match official results.

### 1. Feature state coloring (not data-driven styling)
Map colors are applied via `map.setFeatureState(...)` after data loads, not via MapLibre data-driven paint expressions reading from tile properties. This avoids re-building the style on data change and enables instant re-coloring when the election/round changes.

### 2. Two separate PMTiles files
- `france-admin.pmtiles` — communes (`promoteId: code`) + départements (`promoteId: code`). The dept layer is the base layer **at overview zooms** (see UNDERLAY_HIDE_ZOOM below — it used to be visible at every zoom, and that is what produced slivers). Commune layer has `minzoom: 7`. **Both layers come from one source**: `scripts/build-departements.mjs` fetches all metro + overseas commune contours from geo.api.gouv.fr, tiles them as `communes`, AND dissolves them by département (mapshaper `-dissolve2 fields=dept`, topology-preserving) into the `departements` layer — so every dept boundary is, by construction, a shared commune arc (fixes the old sliver mismatch at the Paris↔petite-couronne boundary, where dept geometry used to come from a different source/vintage). The communes and départements layers are tiled in **separate** tippecanoe runs and `tile-join`ed together (with the PLM arrondissement contours overlaid into `communes`). Separate runs matter: the `communes` run uses `--drop-densest-as-needed` (fine — they're hidden below z7 by the style), but the **`departements` run must NOT** drop features (`--no-feature-limit --no-tile-size-limit`, no drop-densest) — it's the base layer wherever it IS drawn and must keep all 102 features at every zoom it covers. Mixing both into one drop-densest run silently discarded ~half the dept polygons at overview zooms (z4–z6), blanking ~2/3 of metropolitan France. Re-run with `node scripts/build-departements.mjs` (keeps a `.bak`) — don't independently simplify the two layers or the slivers come back.

  **GENERALISED REBUILD (A3, Aug 7 2026) — the tileset is now 45.7 MB, was 86.0 MB.** lucas: "maybe the map is too detailed. It doesn't need to be that close to reality when zooming in". The measurement that framed it: geo.api's IGN contours gave **~1 vertex per RENDERED PIXEL** of outline at z10 (median commune 247 points over a ~250 px perimeter), i.e. most points were below the visible threshold. Two knobs, and **only the second one changes what you SEE**:
  - `--simplify=<metres>` (default **20**) — mapshaper, topology-aware, applied to the communes right after fetching and BEFORE the dissolve, so the dept outline and the PLM arrondissements are generalised from the same arcs. Cut the source 12.8M → 5.5M vertices (−57%) but the TILES only −18%, because tippecanoe already quantises coordinates onto the tile grid (~6 m at z12, ~26 m at z10). Kept because it's free and it keeps the three layers on one set of arcs.
  - `--tippecanoe-simplify=<n>` → tippecanoe `-S` (default **8**) — tile units, i.e. a constant SCREEN-SPACE tolerance at every zoom, which is the right unit for "vertices per pixel". This is the real lever. At z10 (rural Aveyron, 44 communes): `-S1` 10 961 pts / ~1.0 vtx per px / 86.0 MB · **`-S8` 2 973 pts / 1 per ~4 px / 45.7 MB** · `-S20` 1 564 pts / 1 per ~7 px / 35.7 MB. lucas chose 8 (fidelity bias — coastlines still read as themselves; at 20 small inlets vanish and Paris goes polygonal at z12).
  - **No features are dropped at any setting** — verified 44/44/44, 65/65/65, 26/26/26 at z10/z11/z12.
  - **`public/data/geo/overseas.geojson` is REGENERATED from the same arcs (Aug 7 2026) — `scripts/build-overseas-outlines.mjs`, run automatically at the end of a real tile rebuild.** Overseas is the ONE place where three fills stack on the same ground: `overseas-fill` (that file, coloured with the DÉPARTEMENT winner) sits under `communes-fill`/`circo-fill` at every zoom, and it used to come from a different source than the tiles — measured **10.1 px median / 30 px p90** of disagreement in a Guyane tile at z10. That rimmed every overseas coast in the dept's colour (La Réunion in Mélenchon red under orange Macron communes, Mayotte in Fillon blue, Guyane in red) while métropole stayed clean, because métropole has no such layer. **Not caused by A3** — the identical measurement against the pre-A3 tiles gave the same 10.10 px. The script fetches the DOM commune contours, applies the same `--simplify`, dissolves per dept, and PRESERVES the four COM entries (977/986/987/988) untouched: geo.api serves no commune contours for them, so nothing is ever drawn over them and this file is their only geometry. After: **0.10 px median / 0.33 p90 / 0.52 max** (the residual is tippecanoe's per-zoom `-S`, which this file can't have). Cost: 381 KB → 737 KB (100 → 234 KB gzipped), paid on first load by the orbit + mobile overlay.
    - **GOTCHA that shipped once and is worth remembering: RING WINDING.** mapshaper emits RFC 7946 (exterior COUNTER-clockwise); this file's existing convention is the older CLOCKWISE one. MapLibre fills with planar rules and doesn't care, so the MAP looked perfect either way — but the orbit and the mobile overlay draw the same features with **d3-geo, which is SPHERICAL**, and there winding is what separates a polygon from its complement (everything on Earth except it). The mixed file turned every rebuilt DOM silhouette into a filled square (d3 drawing the whole sphere, clipped to the disc) while the four preserved COM entries still drew correctly. `windClockwise()` in the script normalises exteriors CW / holes CCW. Any future generator writing into a d3-consumed GeoJSON needs the same treatment.
  - **RESOLVED for good by the UNDERLAY ZOOM GATE (Aug 7 2026) — `UNDERLAY_HIDE_ZOOM = 8` in FranceMap.** After three reports of the same artifact (métropole dept slivers, overseas coasts rimmed in the dept colour, then the same again on the CIRCO tab) the root cause is one thing: two layers built from different geometry are two independent approximations of the same coastline, and the LOWER one leaks wherever it bulges past the upper one. **No tolerance fixes that** — changing simplification only changes which pixels disagree. So `dept-fill` and `overseas-fill` now go to opacity 0 from z8, where the commune or circo mesh covers everything anyway. The four COM territories (977/986/987/988) are EXEMPT: they have neither commune nor circo polygons, so this layer is their only geometry and gating them would delete them from the map. Measured causes, for the record: `-S8` widened the métropole dept/commune divergence (21%→49% of vertices >2 px at dept 56 z10) but lucas could see nothing, because inland a bulge is hidden under the NEIGHBOURING dept's communes — it can only show at a coast; and on the circo tab, Guyane's circo geometry is a different vintage (11.3 px median vs the commune mesh) while La Réunion's already matched (0.06 px), the visible fringe there being `dept-fill`'s own `-S8` magnified by overzooming past z12. **GOTCHA that blanked the whole map once**: `["zoom"]` may only be the input of a TOP-LEVEL `step`/`interpolate`. Writing the natural `['case', isCOM, visible, ['step', ['zoom'], …]]` fails style validation, and one bad paint expression takes EVERY layer's paint down with it. The gate is a top-level `step` whose above-threshold output carries the COM `case` instead. Also: `applyDeptFocus` writes the same `fill-opacity`, so the focus dimming is composed INSIDE the gate, and the unsettle path resets the underlays to the gate rather than to 1.
- `circonscriptions.pmtiles` — **559** circos (`promoteId: codeCirconscription`), not 577: the four COM circos (977/986/987/988) have never had polygons IN THE SOURCE, which is also why `overseas.geojson` is their only geometry. Overseas circos use Z-codes as feature IDs (`ZA01`…`ZM02`).
  **Rebuilt Aug 7 2026 — `node scripts/build-circonscriptions.mjs`.** SOURCE (it was lost once and had to be re-found; the script header records it): data.gouv **“Contours géographiques des circonscriptions législatives”**, Licence Ouverte 2.0, updated 2024-06-13, aggregated from bureau-de-vote contours — the *p20 simplifiée* resource (~10 MB; the *p10 très simplifiée* one is too coarse for z12). Cached at `data-sources/circonscriptions-p20.geojson`.
  The rebuild does THREE things to the source, and the second one is the important one:
  1. **CLIP to the land outline dissolved from the same commune contours the admin tiles use** (`mapshaper -clip`). Reason: the circo mesh is drawn ON TOP, so the underlay zoom gate can't save it — its own coastline was a different vintage's line and spilled over the water. Interior circo boundaries are untouched: only this source knows them. The script HARD-FAILS if the clip drops any circonscription (that would be a hole in the map and an unreachable territory in the UI).
  2. **FILL the land no circonscription covers** (Aug 7 2026 — lucas reported the artifact a second time *after* the clip shipped, plus "a bug when zooming in too much into Guyana"). Cost: 7.36 → **7.63 MB**.
     **The PLM arrondissements are part of the LAND, not a subset of it** (found chasing Marseille's 1.45 %, which was *not* the split-commune slivers I first assumed). geo.api's contour for Marseille (13055) excludes the **Frioul archipelago, Château d'If and the Riou/calanques islands**, while its contours for the 2e/7e/8e/9e/16e arrondissements include them — and the arrondissements are what the commune layer actually DRAWS there (`NOT_PLM_CITY` hides the whole city). A future election on a DIFFERENT découpage must use its own election's subcom table, not this one.

### 3. Z-code / INSEE bidirectional translation
The circo PMTiles uses Z-codes for overseas features (`ZA01` = Guadeloupe 1ère) but the parsed election JSON uses INSEE-derived codes (`97101`). Two lookup tables in `FranceMap.tsx` handle translation:
- `INSEE_TO_CIRCO_ZCODE` — used when calling `setFeatureState` (map coloring)
- `CIRCO_ZCODE_TO_INSEE` — used in click handlers (so `clickedCommune` holds the INSEE code that `ResultsPanel` can look up)

### 4. Lazy loading of full data
The département-level (`round1.json`, ~107 entries) and circo choropleth (`round1-circ-choropleth.json`) load eagerly. Full commune data (~34 MB) is loaded on demand via TanStack Query's `enabled` flag when the commune tab is active. Full circo data (~0.2–0.6 MB) loads whenever the election has the circo granularity, regardless of tab (July 2026 — the national sheet's Sièges/Circonscriptions view needs it everywhere).

### 5. `clickedCommune` is the universal selection key
The Zustand store field `clickedCommune` stores the INSEE code of whatever is selected, regardless of granularity. `ResultsPanel` resolves it against the appropriate dataset based on `granularity`. Code `'99'` is reserved for the Français à l'étranger aggregate; codes `'9901'`–`'9911'` are the 11 overseas French circos.

### 6. Click event priority on overlapping layers
`overseas-fill` (GeoJSON, always visible) overlaps `circo-fill` and `communes-fill` geographically. The `overseas-fill` click handler calls `map.queryRenderedFeatures` to detect if a more-specific layer was also hit and skips if so. This prevents the dept code from overwriting a circo or commune code.

### 7. `flyTarget` for programmatic zoom
When the user clicks a city from the sidebar list, the component calls `setFlyTarget({ lng, lat, zoom })`. `FranceMap` watches this field and calls `map.flyTo(...)`, then clears it. This avoids passing callbacks between components.

### `src/store/electionStore.ts`
Zustand store. Fields:
- `selected: { type, year, round }` — active election
- `granularity: 'commune' | 'circonscription'`
- `hoveredCommune: string | null` — hovered feature INSEE code
- `clickedCommune: string | null` — selected feature INSEE code (toggles to null on re-click). Deliberately SURVIVES `setSelected` (round/election switches) — it's an INSEE code valid across datasets, so the detail panels re-resolve the same territory in the new data (July 2026 fix; only `hoveredCommune` is cleared).
- `focusedTerritory: string | null` — overseas territory dept code (e.g. '971')
- `flyTarget: { lng, lat, zoom } | null` — consumed by FranceMap, cleared after use
- `flyBounds: [w,s,e,n] | 'overview' | null` — bbox fly request (territory navigator); `'overview'` re-fits metro France with the layout-aware padding. Consumed by FranceMap like `flyTarget`
- `selectTerritory(code)` — sets `clickedCommune` WITHOUT the map-click toggle semantics (navigator/search selections must never deselect)

- `theme: 'system' | 'light' | 'dark'` + `isDark: boolean` — dark mode. `theme` is the persisted preference (localStorage `fe-theme`); `isDark` is the resolved flag. `setTheme` toggles the Tailwind `dark` class on `<html>` (all chrome uses `dark:` variants; `darkMode: 'class'` in tailwind.config) and a module-level `matchMedia('prefers-color-scheme: dark')` listener tracks live OS changes while in `system`. `ThemeToggle.tsx` cycles system→dark→light (desktop top bar; mobile bottom-right chip). The MAP is themed at runtime via `applyMapTheme(map, isDark)` in FranceMap (the style is built once — dark is a `setPaintProperty` pass over background/labels/strokes/fallback-fills, NOT a style rebuild; re-applied after geometry `setStyle` via `isDarkRef`, and `syncMapData` re-runs so the theme-dependent `DEFAULT_COLOR` fallback updates). D3 surfaces (OverseasOrbit, Hemicycle) read `isDark` for their inline SVG colors; the hover tooltip is themed via `.dark .hover-tip` CSS. Data colors (party palettes, gradients) are deliberately theme-invariant.

Also exports `useIsOverview()` — derived selector, true when showing the full-France overview (no selection except the '99' aggregate, no focused territory). Drives the fade-out of the overseas orbit (DesktopLayout) and the wordmark's home state.

### `src/components/OverseasOrbit.tsx` — the overseas ORBIT (redesign R4, July 31 – Aug 3 2026)
lucas's design: every overseas territory in its own floating disc arranged around the mainland. **Equal disc size IS the argument** — lucas's principle of "equally representing all territories (either continental france or overseas)", expressed as geometry.

**It replaced BOTH `AbroadMap` (the top-right world map) and `OverseasInsets` (the left-hand column) — both files are deleted.** One control where there were two; that consolidation is what frees the map's corners for the R3 chrome.

**The arrangement went through three shapes** — worth knowing, because comments and constants that made sense in one are actively wrong in the next (the "which disc binds the width" note below is exactly that trap):
1. **true bearings** on a circle (St-Pierre NW, Antilles W, Pacific E…);
2. **upper-half ring** — all 11 spread over the top semicircle, emptying the bottom arc to let the circle grow;
3. **PARENTHESES (current)** — five discs curving down the left, five down the right, bracketing métropole, with Français de l'étranger lifted out of the arc into the top-right corner. lucas traded the perfect circle away for this ("we might lose the perfect circle position but keep a curved way of displaying the items").

#### Disc anatomy
White disc, silhouette filled in the winner's colour, and a **border made of one arc per CIRCONSCRIPTION**. The first pass coloured only the silhouette on a neutral disc; that FAILED because Polynésie, Wallis-et-Futuna and Nouvelle-Calédonie are scattered archipelagos whose `fitExtent` silhouettes shrink to specks, leaving them effectively colourless. The second coloured the whole disc, which read but lost the shape. lucas's border solves both: **the ring carries the colour at full strength no matter how small the silhouette projects**.

**The border is a stacked bar wrapped into a ring** (`SegmentedRing`) — lucas: "reflect the political balance of the circonscriptions on the colored border… 4/7th of the circle in red, 3/7th in blue". One equal arc per circo, **sorted by palette spectrum order** so identical colours land contiguous (interleaved arcs read as noise, not as a balance) — the same left→right basis the hemicycle uses. Territory circo counts: 971 4 · 972 4 · 973 2 · **974 7** · 975 1 · 976 2 · 977 1 · 986 1 · 987 3 · 988 2 · FE 11, identical across presidential and legislative files. Not decoration: it surfaces splits the aggregate hides — in prés-2022 T2 **Polynésie's dept winner is Macron but 2 of its 3 circos went Le Pen**, and La Réunion is Le Pen overall with 1 of 7 circos Macron.

**The silhouette is split by circo too** when the territory has more than one (lucas). Per-circo outlines live in `public/data/geo/overseas-circos.geojson`, GENERATED by **`node scripts/build-overseas-circo-shapes.mjs`** (decodes the shipped `circonscriptions.pmtiles` with `tippecanoe-decode` at z6, 3-decimal rounding — one rendered pixel is ~5 km of ground at 34px, so both are chosen for size, not fidelity; 86 KB, 19 KB gzipped). **Re-run after any circo tile rebuild**, and remember it is DATA: `public/data` is not git-tracked, so it reaches prod only via `scripts/deploy/sync-r2.sh`.
- **COVERAGE LIMIT**: the circo tileset only ever contained polygons for the **DOM** (ZA/ZB/ZC/ZD/ZS/ZM → 971–976). The COM circos — 977, 986, 987, 988 — have no geometry at all, so **Polynésie (3 circos) and Nouvelle-Calédonie (2) keep a single-colour silhouette**; their segmented border still shows the split.
- **All-or-nothing per territory**: a territory whose circo shapes are only partly available falls back to the whole outline, because drawing a subset would silently misrepresent it as smaller than it is.

**Grouping circos to a territory is by CODE SHAPE**, no lookup table: métropole is a 2-char dept + 2 digits (`3401`, `2A01`), overseas is a 3-char dept + 2 digits (`97401`), abroad is `9901`–`9911`. So length 5 ⇒ overseas (slice(0,3) is the dept), length 4 starting `99` ⇒ abroad.

**Hover opens a per-circo panel** listing each circo with its colour and winner — in circo NUMBER order, deliberately unlike the ring's spectrum order: the list answers "which circo", the ring answers "what's the balance". It lives INSIDE the cell so moving the pointer into it doesn't fire the cell's `mouseleave`. It flips UP for the lower half of each column (so it never runs into the timeline strip) and opens INWARD horizontally — rightward from the west column, leftward from the east and from FE — because a 240px panel centred on a column disc runs off the window edge. On the circo tab its rows are selectable, so the ring doubles as a circo picker; that is what let the old FE click-popover be retired (FE now behaves like every other disc: click selects the `'99'` aggregate).

FE's ring is BROKEN (wider inter-segment gaps) rather than a different size — it has no bearing, so it differs by edge style. With 11 segments that falls out naturally; when circo data is absent it's drawn as 8 dummy arcs of the aggregate colour so the broken edge survives.

#### Geometry — `src/utils/orbitGeometry.ts`
Shared with FranceMap so the arc and the map fit can't drift apart. **The derivation runs MÉTROPOLE-FIRST**, which is the whole point of the current pass: earlier versions sized the arc from the window and gave métropole whatever was left, so on some window shapes the discs came out huge next to a small France and on others the reverse.

1. **métropole takes all the vertical room the chrome leaves** (`TOP_CHROME` 60 / `BOTTOM_CHROME` 76 now bound MÉTROPOLE itself, not the disc rows).
2. **Disc diameter is a fixed fraction of métropole's half-height** — `DISC_OVER_HALF_H = 0.204`, clamped to `[36, 78]`. lucas: "I would like these item and ellipse shape and size to be relative to the position and size of the displayed metropolitan France… so we don't end up with oversized circles compared to continental france on some screen formats or the contrary." Measured constant at **0.102 of France's height** from 992px to 1540px wide; the clamp only bites above that. `CELL_OVER_DISC` (1.45) and `GAP_OVER_DISC` (0.35) scale off it, so cell width, clearance, ring stroke and dash gaps all move together.
3. **The column spans CONTINENTAL France's own north–south extent** — the extreme discs sit at ±(contHalfH − disc/2), so their outer edges land exactly on the north coast and the Pyrenean south. That is lucas's pair of red lines, expressed as geometry (verified live: 0.0px at both ends).
4. **Each column sits one gap out from the land nearest it** — the continent on the west, **Corsica on the east**. So `rxW ≠ rxE` (396 / 462 at a 992px map area) but the *visible gap is identical*, which is what reads as balanced.
5. Only if the window is too narrow for 4 does métropole shrink to fit. On ordinary desktop sizes the **height** budget binds.

- **`CONT = { left 0.024, right 0.904, top 0.012, bottom 0.895 }`** — continental France as fractions of the `METRO_BOUNDS` box, MEASURED against the live projection (Ouessant, Lauterbourg, Bray-Dunes, Cerbère), plus `CORSICA_RIGHT = 0.991`. lucas: "these items should be placed relatively to continental france (corsica excluded)". This matters because the box is not a snug fit — Corsica alone stretches it to 0.991 east and 0.988 south — so measuring the columns from the box left a band of empty sea on the west that had nothing to do with where France actually is.
- **`ASPECT = 1.048`** — the box's projected width/height. Confirmed against the live projection at 1.0478; don't "correct" it from a hand-derived Mercator figure.
- **`STEP_DEG = 15` is the CURVATURE dial** (five discs at steps −2…+2 span ±30°) **and it is not free.** Column height is fixed by 3, so a shallower arc costs nothing vertically — but the bulge is `rx·(1 − cos ext)` and every horizontal px the column takes comes out of métropole. At ±45° the bulge was 29% of `rx` and the WIDTH capped the map at every window size tested; at ±30° it is 13% and the height budget binds instead. lucas asked for "less curved" and the map got bigger with it.
- **GOTCHA — which disc binds the width has CHANGED TWICE.** With the column pinned inside France's band (step 3), the **extreme** discs are the ones furthest in horizontally and they decide the width. In the previous pass, where the ±45° discs sat clear above and below the band, the ±22.5° pair decided it instead. Getting this wrong is not subtle and always shows up in the same place: **Corsica lives in the box's south-east corner, exactly where the lower-right disc lands**, so the wrong choice parks a disc on the island.
- **`metroPadding()` derives the map's fitBounds padding from the same numbers**, and FranceMap **re-fits on resize** (overview only, ResizeObserver, first callback skipped). It also CLAMPS: MapLibre answers padding it cannot fit by logging "Map cannot fit within canvas" and *declining* the fit, which leaves an empty canvas with nothing to retry it.
- **GOTCHA — `||`, not `??`, when reading the container size.** An unlaid-out container reports `0`, not `null`, so `el?.clientWidth ?? 1200` yielded padding larger than its own canvas, the fit was declined, and since the resize re-fit skips its first callback nothing ever corrected it: **métropole simply never appeared**. Latent for a while; the bigger padding of this layout is what exposed it.
- **The disc is anchored on the arc, not the cell.** Labels wrap to one or two lines, so cells differ in height; centring cells put discs off the curve by up to 41px (measured).

**`ARC_SLOTS` ordering** carries geography without true bearings: the west column runs down the Atlantic by LATITUDE (St-Pierre → St-Martin → Guadeloupe → Martinique → Guyane); the east runs Polynésie → Wallis → Nouvelle-Calédonie → La Réunion → Mayotte, i.e. far Pacific at the top down to the Indian Ocean at the bottom (lucas asked for Mayotte and La Réunion at the bottom). Both columns therefore descend by distance from France.

#### Français de l'étranger's corner — and why the util stack moved
FE is NOT on the arc: the arc's order encodes geography and FE has no location, so it floats at `FE_RIGHT/FE_TOP = 12/12`, hard into the top-right corner. **FranceMap's zoom/theme stack moved down to `UTIL_STACK_TOP` (128px) to make room** — the two swapped (lucas).

That swap is not cosmetic. FE used to sit at `right: 64`, dodging the stack sideways, which parked it exactly on the east column's outer envelope: it read as a sixth item in that column, and it tripped the collision rule below, pushing the whole arc — and métropole with it — **70px down the screen**. In the corner FE is ~159px clear of the column, so the arc keeps its full height: at a 1620×1140 map area métropole went **947×904 → 1052×1004**.
- **`UTIL_STACK_TOP` is derived from the LARGEST disc, not the live one**, on purpose: the stack is chrome that exists at every zoom while FE only shows at the overview, so a live-derived offset would shift it during resize and anchor it to something off screen half the time. Accepted side effect: when zoomed in, FE fades out with the orbit and the stack has ~128px of empty map above it.
- The collision rule still exists for narrow windows (it fires at a 992px map area), where FE and the column genuinely overlap.

Every overseas territory, *including the collectivités* (St-Pierre, St-Martin, Wallis, Polynésie, Nouvelle-Calédonie), has a full département-level entry in the data, so the panel resolves all 11 directly; no aggregation was needed. - Colours run through the shared `territoryColor` (all three modes + `decidedAtR1` muting), so the orbit agrees with the map by construction.
- **Visibility + hit-testing — this BROKE map zoom once, so read it before touching:** the orbit's wrapper in DesktopLayout spans the whole map area. Should only be for circo view"). On the communes tab every disc is a single aggregate colour and the silhouette is the whole outline. The reason is consistency, not clutter: the découpage the user picked is the unit the whole map is drawn in, so a ring split by a different one contradicts what's next to it. Gated in `segmentsFor` and in the `silhouettes` memo — `isCirco` is in that memo's dep list, or the split survives a tab switch.
- **The hovered CELL is raised, not the panel** (backlog A1). Each cell sets `transform` and therefore opens its own STACKING CONTEXT, so the panel's `z-20` can't lift it above a cell later in the DOM — it rendered *under* its neighbours. `zIndex: hovered === code ? 20 : undefined` on the cell fixes it. Verified: with Guadeloupe hovered, `elementFromPoint` inside the panel's overlap with the Martinique cell returns a panel row.

#### The phone: ONE button + an overlay ring (M6, Aug 6 2026)
The phone does **not** arrange the territories around métropole. M4/M5 tried that — two flat rows bracketing the mainland — and the arithmetic never got good: eleven touch-sized discs cost ~90px of a budget where France was already the thing being squeezed, and the rows had to dodge every floating control on the way. lucas called it: *"I don't think there's any easy solution on mobile for displaying all overseas territories at once. So I'd rather hide them on mobile behind a single button, that could actually reuse the current symbol of french abroad."*

**`components/OverseasButton.tsx`** — a 52px disc at the map's bottom-left, sitting on the national snippet.
- **The ring is the whole point, not decoration.** Collapsing eleven discs removes eleven results from the screen, so the button puts the BALANCE back: eleven equal arcs, one per TERRITORY, each in that territory's own winner colour. lucas: "I would like all the shares of the circle to reflect the 10 overseas territories and the one french abroad political color for every election. That would be the way to pre-display some kind of detailed results and also to incite the user to click on it." You lose which-is-which; that is what the tap is for.
- Arcs are **equal** (the same "equal standing" argument as equal disc diameters — La Réunion has 660k inscrits and Wallis 8k) and **sorted by palette spectrum**, so identical colours group and eleven arcs read as "six of these, four of those" rather than as a barcode. Sorting is by the COLOUR's index in the authored palette, since a hex is all the segment carries.
- **The globe is filled with the eleven territories' AGGREGATE colour**, so disc and ring stand in the same relation they do on every territory disc: silhouette = who won here, ring = how it breaks down. The aggregate is a real sum of the eleven dept-level rows pushed through `territoryColor`, so it is correct in all three colour modes, not just leader. Verified against the data: prés-2022 T1 → 11 territories, 3 390 418 inscrits, Mélenchon 33,2 % (red globe; ring 6 red / 4 orange / 1 blue).
- Its ring is `broken` — FE's own edge treatment, promoted for the same reason: the button stands for eleven places at once, so there is nowhere to point it.
- Shown on the same gate as the desktop orbit (`isOverview && !zoomedAway && !isHemicycle`), FADED rather than unmounted so the aggregate isn't recomputed on every zoom — with `pointer-events: none` while faded, or an invisible button keeps eating taps over the map.

**`components/OverseasOverlay.tsx`** — what the button opens. lucas: *"a kind of transparent overlay to appear (we still see the map in the BG but with some opacity) that displays a circle of the 11 overseas territories."*
- **The circle works here and only here.** On the map screen a ring would have to be arranged AROUND métropole — which is what forced the desktop's parentheses and the phone's rows in the first place. With the mainland only a dimmed backdrop, the brackets close into a loop.
- **`RING_SLOTS` is that loop**: FE at the apex, then clockwise the east column top-to-bottom down the right side, then the west column bottom-to-top up the left — so on screen the left half still reads St-Pierre → Guyane downward, exactly as on desktop. FE takes 12 o'clock because it is the one territory with no location, which is also why it sits outside the brackets on desktop.
- **An ELLIPSE, not a circle, and CLAMPED.** Stretching vertically buys the one thing no mobile overseas surface has ever afforded: **room for the names**. On a circle at 375px wide the pitch is a uniform ~85px everywhere; stretched, the tight pitch is confined to the apex and nadir and every disc down the sides gets its label back. But left to fill the viewport it reaches an aspect of 2.2 and the discs stop reading as a ring at all — they just look scattered down the two edges (this is what the first pass did). Hence `RING_ASPECT_MIN/MAX` (0.85–1.8).
- **`RING_TOP_PAD = 96` is title clearance, not a margin.** At 56 the apex disc sat 6px under "11 territoires — touchez pour ouvrir" and the globe read as part of the heading rather than as the ring's first item (lucas: "a bit more padding between the circle of overseas territories and the title"). At 96 the gap is 44px and the ring's centre moves down with it. The ring is also CENTRED in its band rather than hung from the top, with `RING_TOP_PAD` as a floor — identical while the band binds, but it stops the ring riding high under the title if the aspect clamp ever bites on a very tall viewport.
- **`RING_BOTTOM_RESERVE` (268) is a PREFERENCE that yields.** Keeping off the snippet+strip band lands the ring over the map, which is what it stands in for — but it is only aesthetic, and at 375×667 it starved the ring badly enough that the flank labels overlapped each other ("St-Martin / St-Barth" ran into "Guadeloupe"). The reserve now gives way toward `RING_BOTTOM_RESERVE_MIN` (88) by exactly as much as the ring needs, where "needs" is solved from the geometry: down the flanks adjacent centres are `ry·sin(Δθ)` apart, and a disc plus its label has to fit in that. At 375×812 nothing is claimed and the ring still clears the card; at 667 it takes ~106px and overlaps the (dimmed, non-interactive) card instead — legibility of eleven names beats not touching a card behind a scrim.
- Tapping a disc settles that territory AND closes (verified: Mayotte → `?territory=976`, sheet shows Le Pen 42,7 %). Scrim tap, ✕ and Escape all close. **Mounted only while open**, so its two GeoJSON fetches happen on the first tap rather than on every page load — which is also why there's no exit transition to match the fade-in.
- Per-circo rings and split silhouettes work here exactly as on desktop, i.e. **circo tab only** (B4).

**`mobileMetroPadding()`** reserves only the search bar at the top now (see the mobile chrome section for the measured effect). It is NOT recomputed on resize — the re-fit effect short-circuits on `mobile` — because a phone viewport only changes on rotation and a re-fit would fight the camera. **Consequence for anyone measuring it in devtools: resizing the browser does NOT re-fit the mobile map, so a resize-then-measure reads stale.** Reload after resizing.

**GOTCHA fixed during M4, pre-existing and desktop-facing:** `overviewZoomRef` was cached on the first zoom event and never refreshed, but the resize re-fit changes the fitted zoom. Widening the window therefore pushed the live zoom above the stale baseline, the map decided the user had "zoomed away", and **the orbit and the national snippet vanished until a reload** — the re-fit effect bails on `zoomedAway`, so it couldn't even correct itself. The resize handler now re-baselines via `cameraForBounds` BEFORE the fit, because `fitBounds` with `duration: 0` fires its `zoom` event synchronously against that ref.

## Data format reference

### `round1.json` / `round2.json` (département level)
```typescript
{
  election: { type: 'presidential', year: 2022, round: 1 },
  candidates: [{ name: string, party: string }],
  communes: [{
    inseeCode: string,   // dept code: '01'…'95', '971'…'977', '986'…'988', '99' (abroad)
    name: string,
    registeredVoters: number,
    turnout: number,
    blankVotes: number,
    nullVotes: number,
    expressedVotes: number,
    leadingCandidate: string,
    candidates: [{ name, party, votes, percentage }]
  }]
}
```
Note: presidential 2022 `round2.json` was REBUILT July 2026 by `scripts/rebuild-dept-from-circ.mjs` (aggregates `round2-circ.json` circos → départements). The original file was corrupt — 101 scrambled entries, 22.7M of 48.7M inscrits, national Macron 71.7% vs official 58.55% — which silently skewed the T2 national summary + dept-level map colors. The rebuilt file matches official totals exactly and includes the previously missing `'99'` (Français à l'étranger) entry. The circo file is the trusted source for that round; re-run the script if it ever regenerates.

### `round1-communes-choropleth.json` (commune choropleth)

{
  granularity: 'commune',
  year: 2022, round: 1,
  candidates: [{ name, party }],
  communes: [{ inseeCode: string, leadingCandidate: string, abstention?: number }]   // ~35,000 entries

```
`abstention` (percent) is added by `scripts/add-choropleth-abstention.mjs` (joins the full-data sibling by inseeCode); it lets the abstention map view render from the ~2 MB choropleth without loading the ~34 MB full commune file. All of France: metropolitan + Corsica + overseas communes (INSEE codes `971xx`–`988xx`, converted from the ministry's Z-codes by `scripts/fix-overseas-codes.mjs`) + consular "communes" of Français à l'étranger (`99001`–`99210`). Overseas communes have no polygons in the tiles, so their entries only serve sidebar lookups (e.g. via the territory navigator), not map coloring.

  communes: [{ inseeCode: string, leadingCandidate: string, abstention?: number }]   // 577 metro + 11 abroad (9901–9911)

```

Same shape as `round1.json` but with `~588` commune entries (577 metro circos with full candidate breakdown + 11 abroad circos `9901`–`9911`).

### `decidedAtR1` — map treatment (R2a, July 20 2026)
At legislative T2, territories flagged `decidedAtR1` are **muted** on every map surface: `decidedAtR1Shade(color, neutral)` in `utils/gradient.ts` blends the winner's colour 55% toward the surface's no-data neutral, so the hue stays identifiable but the territory visibly recedes. `neutral` is theme-dependent (`#e2e8f0` light / `#334155` dark) — blending toward the theme's own neutral is what makes it recede in BOTH themes instead of glowing pale against a dark map. Applied in `computeActiveColors` (choropleth path, FranceMap), `territoryColor` (optional 6th `neutral` arg — dept colours, the overseas orbit) and the orbit's abroad-circo leader path. **Leader mode ONLY** — the party and abstention ramps already encode a value in lightness, so muting there would corrupt the reading. The hover tooltip adds an amber "Résultats du 1er tour — pas de second tour ici" line ABOVE the figures. Round-1 files carry no flags, so T1 is untouched by construction.

**Panels (R2b, July 20 2026)**: `components/results/DecidedAtR1Notice.tsx` — one shared component used by BOTH detail panels (`ResultsPanel` density `compact`, `MobileDetailSheet` density `touch`), rendered ABOVE the participation block so provenance is read before the figures. Its wording adapts to the level rather than the platform: a circo says "Siège remporté dès le 1er tour…", a commune/département says "Pas de second tour sur ce territoire : toutes ses circonscriptions…" ("cette circonscription" would be wrong on a dept). The circo/territory test is `granularity !== 'commune' && !isDeptCode(code)` — a dept code selected from the circo tab still resolves to the dept entry. Unlike the other notices the copy is NOT duplicated per platform (nothing here needs to be shorter on mobile). `DeptInsight`'s Circonscriptions list additionally shows an amber **T1** chip per R1-decided circo plus a decoding sub-line ("9 remportées dès le 1er tour (T1) — résultats du 1er tour pour celles-là") — this is the Paris/légis-2024 case that prompted the whole item: 9 of its 18 circos were decided at T1.

**GOTCHA (cost a full verification cycle)**: the circo CHOROPLETH is what colours the circo map layer, and each parser builds it by projecting explicit fields — so a new field on the full-data entries is silently dropped unless the projection is updated too. All four legislative parsers needed `...(c.decidedAtR1 && { decidedAtR1: true })` added to their `round{N}-circ-choropleth.json` mapping (2022/2024 inline, 2017/agrégées via their local `choropleth()` helper). The commune choropleth was already fine because `carry-r1-into-round2.mjs` copies whole entries. After any change to entry shape, check `-circ-choropleth.json` flag counts match `-circ.json`.

### `decidedAtR1` (legislative round-2 files only)
A circo won outright at round 1 has no round-2 row in the ministry files, so its round-1 entry is carried into every round-2 output to keep the T2 views hole-free (`carryDecidedR1` in `scripts/lib/emit.mjs` for circ files, `carry-r1-into-round2.mjs` for dept/commune/choropleth). Those carried entries — and ONLY those — are tagged **`decidedAtR1: true`**. It means "these figures are the round-1 ones": UI showing a T2 view must differentiate them rather than presenting them as round-2 results. Round-1 files never carry the flag, and presidential files never have it (no `elected`, so nothing is carried). Both carry steps copy rather than mutate and stay idempotent. Counts per election (circos | depts | communes): **2012** 36|1|3 241 · **2017** 4|1|332 · **2022** 5|0|102 · **2024** 76|1|3 852 — the circo figures match each election's official T1 seat count exactly.

## Common gotchas

1. **`makeStyle()` is called once** — never rebuilt. Layer visibility is toggled via `setLayoutProperty`, not by rebuilding the style.
2. **`promoteId` keeps the property** — for vector tile sources with `promoteId`, the promoted property stays accessible via `['get', 'code']` in filter/paint expressions AND becomes the feature ID.
3. **`communes-fill` minzoom is 7** — below zoom 7, tippecanoe has dropped most commune features. The dept fill provides color continuity. Don't rely on commune features being present below zoom 7.
4. **`setClickedCommune` toggles** — calling it with the same code that's already set will clear it (null), because the store uses `s.clickedCommune === inseeCode ? null : inseeCode`.
5. **Overseas commune polygons live in the `admin` tileset too** — `france-admin.pmtiles`'s `communes` layer includes DOM/COM communes (INSEE codes `971xx`–`988xx`), tile-joined in from `scripts/build-overseas-communes.mjs` output (geo.api.gouv.fr contours → tippecanoe → `tile-join` into the existing tileset). They use plain INSEE codes (no Z-codes — those are circos only), so all the existing commune coloring/hover/click paths work unchanged; you must be focused on the territory (zoom ≥ 7) to see them. The `overseasDeptCode()` fallback in `ResultsPanel.tsx` still covers any code that misses commune data.
6. **Tile geometry vs election-data COG drift** — two mechanisms keep every commune polygon resolvable:
   (a) `src/utils/mergedCommunes.ts` (generated by `scripts/build-merged-communes.mjs`) maps obsolete tile codes to their absorbing commune; coloring, hover, click, and selection all translate through it. NOTE: since the June 2026 tile rebuild fetches **current** geo.api contours, the tiles now follow the current COG (not "admin-2022"), so most of those ~406 entries are stale-but-harmless.
   (b) The current-COG tiles instead drift the OTHER way vs the 2022/2024 ministry files: code migrations (Conques-en-Rouergue = COG 12218 vs data 12076) and post-vote défusions (ex-Neussargues villages 15031/…, restored 2025; L'Oie/Sainte-Florence, restored 2024). `scripts/inject-merged-commune-results.mjs` fixes these **data-side** (copies the entry holding the votes under the tile's code, per election — a static map can't express per-election direction). Run it after any parser re-run; it reports still-blank polygons.
   The destroyed WWI villages of the Meuse (55039 etc.) are intentionally blank — they genuinely have no election data.
6. **`flyTarget` is consumed once** — FranceMap sets it to null after use. Don't depend on it persisting.
7. **The overseas orbit stays mounted** — it fades out (opacity + `pointer-events-none`) rather than unmounting, which avoids re-fetching `overseas.geojson` + `overseas-circos.geojson` and re-projecting every silhouette on each zoom.
8. **`circoQuery` is always loaded** — `useCircoChoroplethData` has no `enabled` guard. It always fetches, so the abroad circo results are always available regardless of active tab.
9. **`maplibre-gl.css` is `@import`ed at the TOP of `index.css`** — before the `@tailwind` directives. A CSS `@import` after any other rule is dropped per spec; with it dropped, the map canvas still renders (WebGL) but popups/controls lose their styles (popups fall back to `position:static` and render off-screen). Keep the import first.
10. **Paris/Lyon/Marseille arrondissements** — the `communes` tileset carries the 45 arrondissement polygons (Paris `751xx`, Lyon `693xx`, Marseille `132xx`), tile-joined from `scripts/build-plm-contours.mjs` (geo.api.gouv.fr contours). The whole-city polygons (`75056`/`69123`/`13055`) are kept in the tiles but **hidden at commune zoom** by `NOT_PLM_CITY` (a `filter` on `communes-fill`/`-outline`/`-won`) so exactly one polygon renders per area. Arrondissement *results* come from bureau-de-vote files (`data-sources/burvot-2022/`): the BV code is `AABB` (AA = arrondissement), so `scripts/build-plm-arrondissements.mjs` aggregates bureaux by arrondissement (no REU mapping) and injects entries into the commune full + choropleth files for all rounds. Arrondissements use plain INSEE codes, so all coloring/hover/click/selection paths work unchanged. **Gotcha**: the filter must test `['get','code']`, NOT `['id']` — MapLibre filter expressions evaluate `['id']` against the raw tile feature id (unset; `promoteId` only feeds `setFeatureState` + query results, not filter-time eval), so an `['id']`-based filter silently never matches.
11. **`france-admin.pmtiles` is cache-busted with a `?v=N` query in `TILE_SOURCES` (`FranceMap.tsx`)** — a PMTiles archive is read via byte-range requests against the header + directory at offset 0. When the file is rebuilt (`build-departements.mjs`) the byte layout changes, but the URL is the same, so a browser that cached the old header/directory computes **stale offsets** and reads garbage tile data → metro France renders blank or partial even though the new tiles are correct. **Bump `?v=N` whenever you regenerate EITHER tileset.** Both carry one now — `france-admin` is at v=3 (A3 generalised rebuild), `circonscriptions` at v=3 (rebuilt three times: the clip, the gap fill + full detail at z12, then the PLM arrondissement islands). Symptom of forgetting: the southern/denser half of France is blank at overview while the north renders — looks identical to a tile-drop bug but is purely client cache.
